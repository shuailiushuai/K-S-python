
**结论：**
- 原始C++代码的作者（Marcelo C. Pereira教授）本身就混用术语
- 这不是错误或不一致，而是**反映了组件的本质差异**

#### 2.2.2 为什么不同名称是正确的

| 组件 | Python类名 | 原因 |
|------|-----------|------|
| 劳动力 | `LaborMarket` | **市场机制**：双边搜索匹配算法 |
| 资本 | `CapitalSector` | **生产部门**：容器/聚合器 |
| 消费 | `ConsumptionSector` | **生产部门**：容器/聚合器 |
| 金融 | `FinancialSector` | **金融部门**：容器/聚合器 |

**Labor Market的独特性：**
- 复杂的双边匹配机制
- 跨越两个生产部门（工人可在任一部门工作）
- 678行独立的匹配逻辑
- 松耦合，可独立测试

**Capital/Consumption/Financial Sectors的共性：**
- 主要功能是聚合企业/银行数据
- 与Country时间步协调紧密耦合
- 频繁相互引用
- 主要是统计收集而非独立机制

#### 2.2.3 文件组织合理性分析

**当前组织结构：**

```
python/model/
├── labor.py              # 678行 - LaborMarket（独立匹配机制）
├── country.py            # 2,147行 - Country + 3个Sector（协调聚合）

```

**为什么Labor Market独立？**

1. **功能独立性**
   - 实现复杂的搜索匹配算法
   - 与生产过程无关
   - 可以独立理解和测试

2. **跨部门性**
   - 服务于资本和消费两个生产部门
   - 不属于任何特定部门

3. **代码规模**
   - 678行证明需要单独文件
   - 避免country.py过大

**为什么Sectors在country.py？**

1. **紧密耦合**
   - 与Country的时间步协调频繁交互
   - 相互之间频繁引用

2. **功能聚焦**
   - 主要是聚合和统计收集
   - 不是独立的复杂机制

3. **避免循环导入**
   - 如果分离会导致复杂的相互导入
   - 在一个文件中更容易管理

4. **便于验证**
   - 相关代码在一起更容易与C++对照
   - 清晰的1对多映射关系
